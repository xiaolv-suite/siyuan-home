## 二、 缺陷排查与实测修复证据（Step 2）

按项目实际情况逐类排查 **崩溃/构建类、状态类、数据类、交互类、集成类** 五大维度，不适用项不凑数，命中的 5 项真实缺陷均给出可复现步骤、修复前表现与修复后实测证据：

### 2.1 `[POOL-00 | P0 致命缺陷 · 构建/状态类]` Terser `pure_getters: true` 剥离 Svelte 5 属性 getter 导致生产包全站响应式冻结
- **定位文件**：`vite.config.ts:112`、`scripts/smoke-test.mjs:105`
- **可复现步骤**：
  1. 执行 `pnpm run build` 构建生产包 `dist/index.js`；
  2. 将 `dist/` 部署至隔离思源靶场（`:14680`），在浏览器中打开小驴管家总览面板；
  3. 此时后台扫描已完成（`plugin.scan.reminders.length === 489`），或在控制台调用 `await plugin.addMemo("测试事项", "2026-11-01")` 触发 `emitHubChanged()`；
  4. 观察总览页右上角待办大数字（`.lv-hero-stat-num`）与即将到期列表（`.lv-rem`）。
- **修复前实测表现**：
  - 尽管内存中 `plugin.scan.reminders` 已有 489 条提醒，总览页 `.lv-hero-stat-num` 始终显示 `'0'`，主文案停留在空态 `'先处理重要的事，新想到的内容随手记下。'`，列表显示 `'最近没有要紧事'`（`.lv-rem` 数量为 `0`）；
  - **根因查证**：Svelte 5 将组件接收的 `version` prop 编译为对象 getter（`get version() { return $.get(version); }`），子组件中的 `void version;` 编译为 `void $$props.version;`。v0.5.183 在 `vite.config.ts` 中开启了 Terser `pure_getters: true`，Terser 将所有对象属性读取视为无副作用操作，直接把全站所有 `$derived.by(() => { void version; ... })` 中的 `void $$props.version` 当作死代码剔除（单测因运行未压缩源码而未能暴露）。
- **修复与防回归**：
  - 将 `vite.config.ts` 中的 `pure_getters` 显式设为 `false`；
  - 在 `scripts/smoke-test.mjs` 中新增第 6 项门禁守卫：断言打包后的 `index.js` 必须保留 `.version` 属性访问；
  - **修复后实测结果**：重新构建部署后，靶场浏览器实测 `.lv-hero-stat-num` 立即正确显示 `"490"`，提醒列表渲染 120 张卡片，新增备忘后 DOM 毫秒级实时响应刷新。

### 2.2 `[POOL-01 | P0 缺陷 · 数据类]` 运行态语义指纹遗漏 `trash` 与 `firstRunWelcomed` 导致回收站清空/恢复后重载回滚
- **定位文件**：`src/core/hub/runtime-store.ts:165-303`
- **可复现步骤**：
  1. 启动插件并加载 `hub-runtime.json`（此时 `lastSerializedByPlugin` 记录初始指纹）；
  2. 进入「设置 ➔ 数据与迁移 ➔ 回收站」，点击「清空回收站」（或恢复一条记录，或删除一条未绑定提醒的台账行，此时仅 `rt.trash` 发生变化）；
  3. 触发 `saveRuntime(plugin, plugin.runtime)`，随后刷新/重载思源。
- **修复前实测表现**：
  - `semanticRuntimeFingerprint(rt)` 未包含 `rt.trash` 与 `rt.firstRunWelcomed`，计算出的指纹与内存缓存完全一致，`persistRuntimeSnapshot` 直接 `return` 跳过 `plugin.saveData("hub-runtime.json", snapshot)`，导致磁盘文件未更新，重载后已清空或已恢复的回收站快照重新出现；且 `loadRuntime` 未清洗损坏的 `trash` 数组项。
- **修复与实测验证**：

  - 在 `loadRuntime` 中新增 `normalizeTrash(data.trash)` 过滤非法条目；

## 三、 核心功能全链路验证与半成品清零（Step 3）

### 3.1 半成品识别与本轮全链路补齐

排查发现上一轮对标融合（`b74b87a`）存在 2 处典型的“只写了纯函数或单侧字段，未打通上下游数据源与 UI”的半成品，本轮已彻底补齐：

1. **`[POOL-04 | 半成品补齐 1]` 双基准循环（`recurrenceAnchor: "due" | "completion"`）与 Quick Add `*周期` 语法全链路闭环**：
   - **原半成品状态**：`rule.ts` 写了 `completion` 分支、`AdhocMemo` 定义了 `cycle` 与 `recurrenceAnchor` 字段，但：① `parseQuickAdd` 根本不支持解析 `*周期`；② `complete()` 完成周期备忘时直接设 `doneAt` 终结备忘而不滚期；③ `SchemaLedgerProvider` 扫描家务（`chores`）台账时未读取 `last_done` 列或 `chexecs` 完成流水，导致家务事项永远走不到 `completion` 分支。
   - **本轮闭环实现**：
     - 在 `src/core/quick-add.ts` 实现 `parseCycleToken`，支持 `*每天`、`*每周`、`*每月`、`*每季`、`*每年`、`*14天`/`*2周`/`*3月`、`*每月15号`（含隐含到期日推算）以及按完成日顺延语法 `*!14天` / `*完成后7天` / `*顺延每周`；
     - 在 `overview-quick-memo.svelte` 新增周期预览胶囊并透传 `cycle` 与 `recurrenceAnchor`，在 `calendar.svelte` 当日备忘输入框同步接入 `parseQuickAdd`；
     - 在 `src/core/hub/actions.ts` 的 `complete()` 中：带 `cycle` 的周期备忘完成时自动按 `recurrenceAnchor` 计算并滚动至下一期 `dueDate`；
     - 在 `src/core/hub/providers.ts` 的 `SchemaLedgerProvider` 中：自动提取 `last_done` 列与 `chores` 模块 `chexecs` 最新完成日期作为 `completedDate`，驱动 `recurrenceAnchor: "completion"` 派生下一期提醒。

2. **`[POOL-05 | 半成品补齐 2]` 快速备忘优先级（`!高/!中/!低`）与分类标签（`#分类`）展示及编辑闭环**：
   - **原半成品状态**：`overview-quick-memo.svelte` 输入时显示优先级和分类预览胶囊并存入 `rt.memos`，但保存后在 `reminder-card.svelte`（提醒中枢）与 `overview-upcoming-list.svelte`（总览即将到期）中完全未渲染，且 `openMemoEditDialog` 编辑备忘时无法修改优先级与分类。
   - **本轮闭环实现**：
     - 在 `reminder-card.svelte` 与 `overview-upcoming-list.svelte` 渲染语义化优先级徽章（`.lv-priority-badge--high/medium/low`）与分类标签徽章（`.lv-tag-badge`）；
     - 在 `openMemoEditDialog` 与 `updateMemo` 中支持通过标题语法或补丁对象更新 `priority`、`category`、`cycle`、`recurrenceAnchor`。
